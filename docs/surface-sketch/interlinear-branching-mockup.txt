Claude's notes & my responses:

> **Nothing bounds the preview set**. Six lines is comfortable. A well-explored node with five children each forking again is thirty, and the band swallows the page. The bound is probably already implicit in your design — only show divergences that fall within the preview's own visible span — which would be elegant, since it makes the band's size a function of the space it has. But it needs saying, along with what stands in for the ones dropped.

yes - implicit is the idea, and if it turns out to be unwieldy in practice with a large number of branches, can look at ways to address then

> **Everything below the split still moves down**. Horizontal position is preserved, vertical isn't, and eight inserted lines shove the lower half of the page. Probably fixed by anchoring scroll to the split point rather than the viewport top, but it's the "text changes under you" problem returning by a different door.

yes - the text below that gets dimmed while being pushed down, showing that it's subject to being replaced entirely if a different selection is made at the open branch point

> **The current path appears twice** — as preview line 1 and as the dimmed text below. I think it has to be in the band, since the nested previews need it as their alignment reference, but it shouldn't read as one option among six. It's the you are here, not a choice.

agreed, it appears first amongst the interlineal branches for reference, dimmed or other visual indication that selecting it is a no-op / cancel
